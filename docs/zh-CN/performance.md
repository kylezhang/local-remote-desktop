# 资源占用与性能

[English](../performance.md)

持续共享桌面会占用 CPU、内存和网络。目前没有完整双机性能基准或数小时持续运行结果，不能保证绝无卡死、死锁或内存泄漏。

## 当前的资源约束

- 检查到的接收、管道读取、输入队列、重连循环会等待数据或延时，没有发现无等待的空转循环。重连间隔 3 秒，认证和网络接收有超时。
- Mac 的 ScreenCaptureKit 队列深度为 3，同时最多提交 2 帧编码；负载过高时在编码前丢弃原始帧，要求 VideoToolbox 硬件编码。这是源码检查，未测 Mac 真实占用；系统采集/编码的启动、停止调用仍可能卡住。
- Windows 只保留一帧待显示画面，输入队列最多 256 项并合并连续鼠标移动。FFmpeg 错误输出改为固定缓冲读取，避免长时间累计。
- 未连接时停止画面刷新计时器；关闭窗口时直接结束本窗口的解码进程，避免应用退出导致异步清理未完成。不会结束其他 FFmpeg 进程。

Windows 仍使用 FFmpeg 软件解码和 WPF 图像复制。每帧新建 BGRA 数组，1080p/60 约产生 **498 MB/秒内存分配**。这不是常驻内存或网络流量，但频繁垃圾回收可能影响流畅度。复用画面缓冲、硬件解码和渲染仍需优化。

## 2026-10-09 测量范围

向产品解码器按帧率输入合成 H.264，各运行 40 秒。测试程序包含数据生产；不包含 Mac 采集、网络传输和 WPF 显示。本机有 32 个逻辑处理器，CPU 数值按整机总能力计算，不能当成单核百分比或其他电脑的预测。

| 测试 | 解码帧率 | 测试程序 / FFmpeg 专用内存范围 | 测试程序 / FFmpeg 平均 CPU |
|---|---:|---|---|
| 1280×720，30 fps | 29.73 | 25.6–36.8 / 57.3–57.7 MiB | 0.77% / 0.69% |
| 1920×1080，60 fps | 59.46 | 120.6–147.1 / 76.2–84.1 MiB | 1.70% / 1.62% |

短测中采样内存未持续上涨，但两档约每秒发生 10 次第二代垃圾回收，说明分配压力确实存在。第二档沿用第一档的测试进程，不能把它的内存当成独立客户端占用。这些结果不证明长期无泄漏，也不代表完整远控的占用。

两次解码结束后进程均退出；另用真实 WPF 客户端连接模拟端验证断开、切档，以及连接中关闭窗口的清理。资源测试还覆盖固定缓冲读取 256 MiB 逻辑错误流、取消读取，以及在启动解码器前拒绝超大画面。

更新后的真实客户端未连接观察 30 秒：整机平均 CPU 为 0.010%，专用内存 106.3→106.1 MiB，窗口有响应，最后检查只有一个窗口且没有 FFmpeg 子进程。这是同一台 32 逻辑处理器电脑的空闲观察，不是共享期间的占用。[空闲记录](../../tests/results/resources-idle-2026-10-09.json)。

[原始资源记录](../../tests/results/resources-2026-10-09.json)。运行方式见英文页，支持每档 20–600 秒。

资源紧张或操作不顺时可选“流畅”（最高 720p/30）。标准、高清目标最高 1080p/60，码率不同；实际尺寸保持 Mac 屏幕比例。后续需要完整会话的长测、重复重连、休眠唤醒，以及 Mac 的 CPU、内存和能耗实测。

## 文件传输速率控制（开发更新）

持续目标 8 MiB/s、起始 512 KiB 额度，按单调时间计入磁盘/网络耗时，移除逐块固定等待，保持 32 KiB 分块且不新增无界发送队列。三次本机加密模拟传输中，8 MiB 完成耗时中位数由 4009 毫秒降至 954 毫秒；256 KiB 由 126 毫秒降至 3 毫秒，首次冷启动为 171/39 毫秒。这不代表实机局域网速度或带宽竞争表现。

维护者可为 FileChecks 设置 `LOCALREMOTE_FILE_BENCH` 为 JSON 输出路径运行基准，取消变量运行正常检查；使用合成文件而非真实剪贴板。见[验证记录](../../tests/results/file-speed-2026-10-09.txt)。
